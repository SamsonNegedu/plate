# Phase 2 — Data model, migrations, FTS5

Status: done
Depends on: 1
Blocks: 3, 4, 6

## Goal

A schema that makes the product's rules impossible to violate in the database, with migrations, generated queries, and FTS5 search in place before any endpoint uses them.

## Schema rules

- IDs are UUIDv7 text, generated by the client for entries and by the server for reference data.
- Timestamps are UTC RFC 3339 text. Local dates are `YYYY-MM-DD` text.
- Nutrition is stored per 100 g/ml. Missing nutrients are `NULL`, never `0`. A food is loggable only when `kcal_100g` is not null.
- Every syncable row carries `user_id`, `created_at`, `updated_at`, `deleted_at`, and `server_seq`.
- Deletes are tombstones. No hard deletes for syncable rows.
- `server_seq` is assigned from the per-user change stream, so it is monotonic and gap-free per user.
- Foreign keys are on. Cascades are explicit.

## Tables

### `users`

`id` PK, `email` unique not null, `password_hash` not null, `created_at`, `updated_at`.

Exactly one row in v1. A partial unique index on `email` is unnecessary; `email` is unique.

### `sessions`

`token_hash` BLOB PK, `user_id` FK, `data` BLOB, `expiry` text. Index on `user_id, expiry` for logout-all and cleanup.

The cookie carries the token; the database stores only its SHA-256 hash.

### `settings`

`user_id` PK/FK, `goal_kcal` int not null, `protein_g`, `carbs_g`, `fat_g` int not null default 0, `day_start_hour` int not null default 0 check 0–23, `theme` text check `auto|light|dark`, `updated_at`, `server_seq`.

### `foods_fts`

FTS5 external-content table over `name`, `brand`, `barcode`, `content='foods'`, `content_rowid='rowid'`, `tokenize='unicode61 remove_diacritics 2'`.

Triggers maintain it on insert, update, and delete. Include `barcode` so an exact numeric query can match, but rank it low. The endpoint checks exact barcode first anyway.

Optional, only if the German fixture suite fails: `foods_trgm` with `tokenize='trigram'` for substring matching. It is not added speculatively.

The snapshot is the point. If OFF corrects Nutella next month, last month's log must not change.

### `saved_meals` and `saved_meal_items`

`saved_meals`: `id` PK, `user_id`, `name`, timestamps, `deleted_at`, `server_seq`.

`saved_meal_items`: `id` PK, `saved_meal_id` FK cascade, `food_id` null, `name` snapshot, `brand` snapshot, `amount`, `unit`, `grams`, per-100 g snapshots, `position` int. Items are snapshots so a renamed or deleted food does not break a saved meal.

### `favorites`

`user_id`, `food_id`, `created_at`, PK `(user_id, food_id)`. Favorite is a relation, not a food field.

### `change_log`

`seq` INTEGER PRIMARY KEY AUTOINCREMENT, `user_id`, `entity`, `entity_id`, `op` (`upsert|delete`), `payload` JSON text, `created_at`.

Index `(user_id, seq)`. This is the sync source of truth. The payload is the full row after the change, so pulls need no joins.

Retention: rows older than 180 days are pruned, and `sync_state.min_seq` advances. A client below it must snapshot.

### `sync_state`

`user_id` PK/FK, `min_seq` int not null, `head_seq` int not null, `updated_at` text not null.

`change_log.seq` is global. `min_seq` and `head_seq` are per user, computed from that user's rows only. A client cursor is compared only to its own user's `min_seq`; another user's pruning must never force a resync.

### `sync_ops`

`op_id` text PK, `user_id`, `client_id`, `applied_at`, `server_seq`. Index `(user_id, applied_at)`.

Used only for idempotency. A duplicate `op_id` returns the stored result.

### `search_cache`

`key` text PK (normalized query hash), `response` text, `expires_at`. Index `expires_at`. Pruned on startup and daily.

### `image_cache`

`key` text PK, `content_type`, `bytes` integer, `fetched_at`, `last_used_at`. Index `last_used_at`. Files live under `data/images/<key>`; the table tracks metadata and enforces the size bound.

### `meta`

`key` text PK, `value` text. Required keys: `schema_version`, `off_import_state` (optional). Per-user sync cursors live in `sync_state`, not here.

## Migrations

- goose files under `db/migrations`, zero-padded: `00001_init.sql`, `00002_search.sql`, ...
- Multi-statement triggers use `-- +goose StatementBegin` / `StatementEnd`.
- Every migration has a `down` that reverses it locally.
- Production migrations are additive. A breaking change is expand/contract over two releases.
- Before applying migrations, run `VACUUM INTO data/snapshots/pre-migrate-<ts>.db`.
- Run migrations before opening the listener. `/readyz` fails while migrations are pending.

## Transaction policy

- One `*sql.DB`. Pool size 4.
- Write paths use a helper that acquires a `*sql.Conn`, executes `BEGIN IMMEDIATE`, runs the function, then commits or rolls back.
- Read paths use the same pool; WAL allows concurrent readers.
- `busy_timeout=5000`; on `SQLITE_BUSY`, retry the whole transaction up to three times with jitter.
- Never hold a transaction across a network call. OFF and image fetches happen before the write transaction.

## sqlc and repository boundary

- `sqlc.yaml`: engine `sqlite`, schema from `db/migrations`, queries from `db/queries`, output `internal/store/sqlc`.
- Generated code is committed.
- A repository layer maps generated rows to domain models. Handlers never import sqlc types.
- `sql.ErrNoRows` maps to `domain.ErrNotFound`.
- Dynamic filters (date ranges, search options) use explicit query variants rather than string building. If a variant is unreasonable, use a small query builder in the repository, never in a handler.

## Maintenance

A daily in-process job runs:

- `PRAGMA optimize`.
- `PRAGMA wal_checkpoint(TRUNCATE)`.
- Search-cache expiry.
- Image-cache LRU eviction.
- `change_log` retention and `sync_state.min_seq`/`head_seq` refresh.
- Stale `sync_ops` pruning.

No cron and no external CLI. The job has a context, is idempotent, and logs counts.

## Tests

- Migration up, down, up on a temp file.
- Schema snapshot test to catch accidental drift.
- FTS: every German fixture query returns the expected top 3.
- Catalog import: duplicate barcodes resolve last-wins within the seed; rows without kcal are skipped; a re-import replaces the table in one transaction; a missing/empty file leaves the old catalog intact.
- A catalog row is loggable without a matching `foods` row.
- Partial unique barcode: two live rows with the same barcode fail; a tombstoned row does not block a new one.
- Cascades: deleting a saved meal removes items; deleting a user cascades as designed.
- `server_seq` monotonic per user; no gaps in the change stream.
- `sqlc diff` clean.

## Note

Verified: `make verify` exits 0; `make migrate-up`, `migrate-down`, `migrate-up` on a fresh file; schema, constraint, cascade, FTS (German fixtures, update and delete), snapshot-before-migrate, and 64-writer concurrency tests pass; `sqlc diff` clean.

Decisions made while building:

- `server_seq` on rows is the `change_log.seq` of the change that wrote the row. The stream is global; a user's own sequence is monotonic and, with one user, gap-free. Sync phases rely on monotonic, not gap-free.
- `favorites` gained `updated_at` and `deleted_at`, and `settings` gained `created_at` and `deleted_at`, so removals sync as tombstones (no hard deletes). `sync_ops` stores a `result` JSON so a duplicate `op_id` returns the original outcome. `catalog_foods` stores `scans` for ranking ties and uses an integer key for the external-content FTS table.
- FTS tables use `prefix='2 3'` so short queries need no LIKE fallback (Spike B).
- sqlc needs `db/sqlc/fts_stub.sql` to type-check `MATCH` and `bm25`; it is never applied to a database.
- sqlc drops parameters when `BETWEEN` is combined with named args, so range queries use `>=` and `<=`.

Not done here: catalog import tests (duplicates last-wins, rows without kcal skipped, atomic replace, missing file keeps old catalog) belong to the importer in Phase 5. FTS ranking beyond the German fixtures is Phase 5.
